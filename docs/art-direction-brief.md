# Art direction brief — персонажи Allods Home

> Рабочий документ по шаблону скила `create-game-assets`. Статус: **черновик — ждём одобрения визуального эталона (маг-мужчина)**.
> Провенанс генераций: `bl image` (Aliyun Bailian), все кандидаты проходят ручное одобрение пользователя.

## Game frame

- Player fantasy: тактический RPG-герой в фэнтези-песочнице («духовный наследник Аллодов II», не копия)
- Core verbs: исследовать, сражаться (активная пауза), нанимать отряд, крафт, торговля
- Engine and renderer: Godot 4.7, GL Compatibility, 2D
- Target platforms: Windows (дальше — Steam/itch)
- Camera/view/facing: изометрия 3/4 сверху; юнит рисуется в **5 направлениях** (вниз, вниз-влево, влево, влево-вверх, вверх), правые 3 направления — H-flip зеркала (отдельных кадров нет)
- Native viewport and common display scale: референс 1280×800
- Typical asset size on screen: кадр юнита 128×128 px, тайл 32 px, якорь (cx,cy)=(64,78)

## Visual system

- Shape language: умеренно-угловатые фигуры, читаемые силуэты; маг — высокий, средний телосложение, вертикальный силуэт мантии
- Silhouette priorities: на 64×64 должны читаться класс (маг/воин), пол, поза; плащ/мантия не сливаются с фоном
- Value structure: 3–4 тоновых плана; персонаж светлее/контрастнее тайлов земли
- Palette roles and exact swatches: **зафиксированы по одобренному эталону mage_m_target_001 (2026-09-25):** мантия сине-фиолетовая — `#666699` (основная), `#555588`/`#444477`/`#444466` (средние тени), `#333355` (глубокая тень); волосы/кожа-коричневый — `#775533`, `#664422`, `#553322`; тёмное — `#332211`, `#221111` (контур/провалы). Акцент класса — золото трима (уточнить при производстве). Для воина — своя палитра после его эталона
- Materials and surface cues: ткань (мантия) — мягкие складки; кожа — матовая; металл — узкие яркие блики; дерево посоха — тёплое
- Edge/line treatment: тёмный контур 1 px (не чисто-чёрный — тонированный в локальный цвет), без «грязных» одиночных пикселей
- Lighting direction and contrast: свет слева-сверху, мягкий ambient; допустим слабый rim-light справа-снизу; запечённых теней от сцены нет (тень рисуется кодом отдельно)
- Detail density and focal hierarchy: детализация выше 1999 г. (заказ пользователя «уже 2026»): богатая палитра (~48–64 цвета на персонажа), плавные шейдинг-переходы кластерами 2×2+, фокус деталей — голова/плечи/оружие; низ мантии проще
- Motion character: сдержанно-весомая (как оригинал), без squash&stretch
- Explicit exclusions: фотореализм, 3D-рендер-look, аниме-глаза, неоновая палитра, текст/подписи на арте

## Technical contract

- Asset dimensions/aspect: кадр 128×128; холст генерации-исходника 512×512 (даунскейл)
- Alpha/background: прозрачный фон (генерация на пурпурном #FF00FF + программный кеинг Python/PIL)
- Grid/tile/frame size: раскладка набора героя — **129 кадров** (idle 9; move 5×10; attack 5×7; dying 5×4; decay 5×3; направление-мажор: frame = block_start + dir×phases + phase)
- Anchor/pivot/baseline: (64,78), низ спрайта = точка контакта с землёй
- Filtering/mipmaps/compression: nearest (пиксель-арт), mipmaps off, lossless PNG
- Color space: sRGB
- Texture/poly/material budgets: один набор ≈ 129×128×128×4 Б ≈ 8.4 МБ в памяти; цель — не превышать текущее число наборов (30 heroes)
- Naming and folders: `assets/units/heroes{,_l}/<set>/sprites-NNN.png` — формат и имена НЕ меняются (код `UnitAnim`/`anim_set_name()` не трогаем); новые тела/слои — `assets/units/_layers/` (wip — вне git до одобрения)

### Hero-контракт «набор из ИИ-полос» (14.10, проверен игроком в игре)

Действует для `hero/war_men` и будущих наборов, которые рисуются генератором
полос. Это **третий** контракт рядом с hero-128 и NPC-A, и он их не заменяет.

| Поле | Значение |
|------|----------|
| Холст кадра | **64×64** (как NPC-A) |
| Content-рост фигуры | **54 px** (`TARGET_H` в `tests/extract_hero_nb.py`) |
| Feet | низ контента = **y 62** |
| Ракурс | **один нарисованный**, три четверти (~30° к зрителю) вправо |
| Направления | `dirs: 1` — запад = зеркало `flip_h`; север/юг «скользят» прежним боком |
| Раскладка | `idle 1 + move 4 + attack 3 + dying 4` = **12 кадров** |
| Блоки в базе | `idle=0`, `move=1..4`, `attack=5..7`, `dying=8..11` |
| Ширина/высота силуэта | **0.36…0.59** (городские NPC 0.36…0.59) |

**Почему 4 панели на полосу, а не 8.** Замер: 8 фигур по ~190 px на 1536 px
физически не помещаются — в промежутках удара было 15–72 px чужой руки, в
промежутках смерти до 234 px. Четыре фигуры занимают по ~380 px, зазоры
50–285 px.

**Почему удар из 3 фаз.** В полосе 4-я панель совпала с 3-й (та же полная
вытяжка). Цикл замыкается сам: стойка → замах → удар → возврат в стойку.

**Правила промта, без которых фигура получается «жердью»:**

- **ЗАПРЕЩЕНО слово `lean`** в описании персонажа — модель рисует худого буквально.
  Вместо него `broad-shouldered, sturdy`.
- **ЗАПРЕЩЁН `SIDE VIEW`.** Профиль — самый узкий силуэт: видно только бок,
  второе плечо спрятано. Даёт 0.24 ширины к высоте. Нужен разворот ~30°.
- Телосложение и ракурс ставятся **до** описания позы: узкий `SIDE VIEW` в
  конце промта перебивает `broad` в начале.
- Фон — плоская мажента (255,0,255), **без тени, пола и линии пола**, зазоры
  между фигурами ≥ 40 px.

**Конвейер (не тратить деньги вслепую):**

1. Правим промт, а не режем картинку.
2. Генерируем **одну** полосу `stand` — самая дешёвая проверка ракурса и
   телосложения.
3. Гоняем preflight по тому же файлу — он печатает толщину каждой фигуры.
4. Только после «ГОДЕН» добираем остальные полосы и собираем набор.

| Скрипт | Роль |
|--------|------|
| `tests/gen_hero_strip.py` | генерация полосы + preflight (фон, фигуры, зазоры, тень, ноги, **толщина**) |
| `tests/extract_hero_nb.py` | нарезка полос в 12 кадров + `_contact_sheet.png` + `_entry.json` |
| `tests/facing_probe.py` | замер направления по центру кожи лица |
| `tests/crop_rows.py` | отрезает верхний ряд, если модель вернула 8 фигур в два ряда |
| `tests/hero_size_probe.gd` | замер силуэтов героя и NPC в игре (ширина/высота в пикселях) |

**Что нужно на машине разработчика:**

- **Пересобрать набор из уже готовых полос — ключ НЕ нужен.** Исходники
  `import/Player/hero_{stand,walk,attack,die}_nb5.png` лежат в git, нужны
  только `numpy` и `pillow`: `python tests/extract_hero_nb.py`.
- **Сгенерировать новые полосы — нужен ключ KodikRouter.** Он намеренно НЕ в
  git и НЕ в папке проекта (`.gitignore: *.kodik_key` — страховка). Ключи лежат
  вне репозитория: `%APPDATA%\Mirotokhome\kodik_key` и `kodik_audio_key`;
  альтернатива — переменная окружения `KODIK_API_KEY`. Без ключа
  `gen_hero_strip.py` завершается понятным сообщением, а не ошибкой 401.
- Первый запуск Godot после `git pull` требует `--headless --import`: кэш
  `.godot/` в репозитории не лежит, и без импорта глобальные классы
  (`Game`, `UnitDB`, `SpellDB`) не зарегистрированы — см. §3.
- Пути к двум машинам и к Godot — §2.

### Контракт монстра (15.10, тот же конвейер, другая анатомия)

| Поле | Значение |
|------|----------|
| Холст кадра | **64×64** |
| Content-рост | вписывается **по обеим осям**: `TARGET_H=54`, `TARGET_W=62` |
| Feet | низ контента = **y 62** |
| Ракурс | один нарисованный, три четверти (~30°), `dirs: 1` + зеркало |
| Раскладка | `idle 1 + move 4 + attack 3 + dying 4` = **12 кадров** |
| Блоки в базе | `idle=0`, `move=1..4`, `attack=5..7`, `dying=8..11` |
| Летающие | поле `z` в `units_db` (bee 24, bat 32, ghost 28, dragon 40) |

**Масштаб по обеим осям — обязателен.** Раньше считался только по высоте, и
бегущий волк (1148×529 px в исходнике) после подгонки под 54 px становился
117 px шириной при холсте 64: `paste` срезал по 26 px с каждой стороны, и в игру
уезжали **волки без головы**.

**Фигуры считать связными компонентами, не колонками.** У соседних зверей
хвост/лапа/крыло соприкасаются, колоночные прогоны сливаются в один, и порог
«шире медианы» не срабатывает никогда — медиана посчитана по тем же слипшимся
кускам.

**Раскладку модели не контролировать.** На одну просьбу «4 фигуры в ряд» она
даёт 4×1, 4×2, 2×2 и лесенку по диагонали. Нарезчик обязан понимать все формы.

**Вид движения и тип атаки задаются по зверю**, а не одни на всех:
`run` / `fly` (взмах крыльев) / `hover` (парение дрейфом, `NO WINGS of any kind` —
без него призрак отращивает крылья); атака `bite` / `sting` / `breath` / `cast`.

**Женский персонаж требует отдельного описания.** Замена местоимений
(`femaleize()`) не даёт ни одной женской черты, и модель спокойно рисует
мужчину: та же стойка, тот же кирас, те же плечи.

### Правила промта, проверенные на тролле и суккубе (17.10)

Эти четыре правила стоили $0.31 вслепую и повторяют ошибки, которые уже описаны
выше, но в новой формулировке.

**1. Слова размера сильнее числового запрета.** Тролль с описанием «huge massive
broad-shouldered» лез в полосу три раза подряд: 600 px при норме 557 (22% кадра).
Правило «не шире 20% ширины» модель проигнорировала **дважды** — и на второй раз
нарисовала 8 фигур вместо 4. Помогло не усиление запрета, а **уменьшение
требования**: убрать «huge massive» и заменить на компактное описание. В игре все
Серые ~54 px, поэтому «огромный» на картинке не даёт ничего, а ширину портит.

**2. Вертикальный инструмент в руке сужает силуэт.** Дубина «на плече, торчком
вверх» вместо «в руке сбоку» — бесплатный способ вписать крупного зверя в узкую
полосу, и это ничего не меняет в характере существа.

**3. Крылатое существо не влезает в четыре панели в ряд — это анатомия.** У
суккуба ширина фигуры при падении растёт 467 → 640 → 666 → **725** px, и сумма
четырёх панелей **не помещается в холст 2528 px даже без зазоров**. Успешная фаза
полёта работала только потому, что крылья были описаны отдельной фразой. У падающей
фигуры крылья расправляются сами, если не сказать обратное.

**4. Смерть крупного зверя — вертикальная поза, а не «лежит плашмя».** По решению
игрока смерть суккуба — **оседание на колени**: тело вертикально, крылья сложены,
ничего не распластано по земле. Попытка прошла с первого раза. Для крупного
двуногого существа падение плашмя — это заведомо более широкая фигура, чем стоячая.

### Набор может существовать без фазы удара (17.10)

`extract_monster_nb.py` не требует полосу `attack`. Набор собирается из трёх фаз
(стойка 1 + ходьба 4 + смерть 4 = 9 кадров), в `_entry.json` честно пишется
`attack: 0`, а в описание добавляется пометка `NO ATTACK ANIMATION`. Прецедент в
проекте был — `ork_mage` живёт без анимации удара, урон при этом наносится.

Смещение блоков в `unit_anim.gd` считается из числа фаз, а не из жёстких
индексов, поэтому нумерация кадров при 9 вместо 12 учитывается сама.

⚠️ Отброшенную полосу надо **физически убрать** с диска: инструмент подхватит её
сам и соберёт набор с дефектной фазой. Это случилось один раз.

### Тиры через перекраску, а не генерацию (17.10)

Тир — это цветовая копия набора, а не новое существо. Один вид = 4 перекраски,
$0 вызовов API против ~$0.24 за генерацию.

- **Цель тона у каждого тира своя** (`TIERS`), иначе тир 5 волка вышел бы
  фиолетовым, а тир 5 призрака — жёлтым: сдвиг считается от палитры исходника.
- **Тон центрируется на цели**, а не «притягивается» к ней: притяжение ломается,
  когда база почти противоположна цели (динозавр 26° → цель 205° давал 133°).
- **Тир 2 у большинства видов отличается тоном недостаточно** — у 4 из 7 нативный
  тон совпадал с целью в пределах 1–12°. Различает его насыщенность и светлота
  (`×1.55` / `×0.72`), а не тон.
- **Контрактные поля тирной копии копируются из `_entry.json` базового набора**,
  а не задаются константами в генераторе: константа `attack: 3` молча пообещала бы
  анимацию удара набору, у которого её нет.
- **`z` летающих переносится автоматически** тем же путём.

### Цвет: фиолет может быть в промте, а не в нарезке (17.10)

Остаточная маджента и «фиолетовый арт» — разные вещи, и замер по магенте даёт 0%
там, где объект на 89% сине-фиолетовый. У `tree_dead` виновником был промт
`twisted **grey** branches, **haunted swamp** tree`: модель отрисовала серый как
фиолетовый. Лечится прямым запретом `STRICTLY NO purple/violet/blue` плюс
требование палитры уже принятого объекта (дуба).

⚠️ Не измерять «розовую кайму» условием `r>g and r>b`: это ловит **бурую
древесину** — `prop_sack` дал 100%, `prop_crate2` 99.9%, и метрика объявила
дефектом 19 нормальных файлов.

### Модели и цены — важнее, чем кажется (15.10)

`tests/model_prices.py` — цены лежат не в каталоге `/images/models`, а на
`/images/models/<id>/endpoints`. Полный список — там же, с `--free`.

| Модель | Цена | Вердикт |
|--------|------|---------|
| `inclusionai/ming-image-0.1-design` | $0 | задокументирована как бесплатная, `/images` отдаёт **404** — провайдер не заведён в маршруте |
| `seedream-5-0-flash` | $0.018 | **теряет субъект между вызовами**: стойка и бег вышли разными зверями |
| `gemini-nano-banana-2.1` | ~$0.06 | держит субъект, квота кончается после ~$1.7 за день |
| `gemini-3.1-flash-image-preview` | $0.10 | держит субъект, квоты не жмёт |

**Вывод:** дешёвая модель есть, но «простые атласы» она не вытягивает — набор
из нескольких полос требует модели, которая помнит персонажа между вызовами.

**Две известные дырки в инструментах (не починены, записаны честно):**

- Порог толщины 0.36 даёт **ложную тревогу на компактных позах**: в стойке с
  кулаками у груди силуэт 0.29, и это правильная анатомия, а не жердь.
- Замер направления **не работает на позах с поднятой рукой**: кулак попадает
  в полосу «головы» и раздвигает её. На стойке и ходьбе признаки сходятся.


## Персонажи (матрица)

- Пол: male / female — **должен быть виден в игре** (сейчас `Game.hero_gender` не влияет на спрайт — исправим через разные базовые тела)
